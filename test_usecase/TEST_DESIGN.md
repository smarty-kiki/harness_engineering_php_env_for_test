# 综合测试设计指南

本指南说明如何从真实使用入口设计测试用例，重点覆盖正常流程之外的失败、数据丢失、写入落库和可逆操作边界。它属于 harness 的通用方法，不包含任何具体项目的用例或数据。

设计时先问四个问题：

1. **依赖不可用时，用户看到什么、还能做什么？**
2. **底层数据不存在或与页面状态不一致时，操作会怎样？**
3. **这次操作写入了什么，数据库里真的对吗？**
4. **可逆操作执行后，能否正确回退，重复执行是否安全？**

## 1. 按入口分层设计（页面优先）

| 入口 | 优先测试内容 | 不适合的场景 |
|------|--------------|--------------|
| 页面 | 用户可见流程、表单校验、提示、按钮状态、跳转、空态、权限表现 | 需要构造大量参数矩阵、直接协议调用、无法通过 UI 触发的异常分支 |
| 接口 | 参数边界、鉴权、状态机、分页、并发/幂等、异常返回、跨资源隔离 | 纯展示效果、页面交互 |
| CLI | 命令参数、退出码、交互确认、批处理、回滚、依赖不可用时的诊断 | 页面展示 |

**页面优先**是硬约束：同一段行为优先从页面穿透，页面确实不可达或难以稳定触发的，才用接口或 CLI 补测。三层用例统一计入通过率，不应把某一层的问题隐藏成“只在前端测不到”。

结果 JSON 里必须说明补测原因：

- `via_page`：对应的页面用例名（同一行为已能从页面触发）。
- `unreachable_reason`：页面不可达的具体原因（仅展示、并发构造、协议级异常等）。

两者至少写一个；页面可达却只写接口用例、又不说明原因，报告会判为「页面穿透未分类」。`run-all.sh` 默认严格审计（`AUDIT_STRICT=1`）。

## 2. 接口不可用 / 异常响应

模拟角度：

- **网络失败**：请求被拒绝、连接中断、超时。
- **服务端错误**：HTTP 500/502/503、业务错误码、非 JSON / 空响应。
- **慢响应**：延迟返回、长时间不返回。
- **鉴权失败**：未登录、会话过期、无权限、Key 被撤销。
- **部分失败**：页面首屏多个接口中一个失败、列表分页中某一页失败、弹窗依赖数据失败。

检查点：

- 不出现**假成功**：不能显示成功 toast、不能把未写入的数据渲染成已保存、不能静默刷新成成功态。
- 错误对用户可见且可理解，不能白屏、无限 loading、弹原生错误框或只留下空页面。
- 操作控件能恢复：按钮解除禁用、表单可重新提交、弹窗可关闭、重试不会重复提交。
- 无未捕获前端异常、无未处理的 Promise、无控制台致命错误。
- 失败后页面仍可继续操作其他功能，不污染已有数据。
- 重复提交 / 重试具备幂等性或明确防重提示；慢响应期间有 loading 或禁用态。
- 失败路径同样检查落库：失败请求不应产生半条记录或部分写入。

断言应写入用例的 `expected` / `actual`，失败不中断后续用例。

## 3. 底层数据被删除 / 状态不一致

删除时机：

- 页面加载前删除；
- 详情页已经打开后删除；
- 用户点击保存 / 状态流转 / 确认弹窗时删除；
- 关联数据先删除，主数据仍在。

删除对象：

- 主记录（项目、任务、单据等）；
- 关联记录（成员、版本、配置、关联资产）；
- 凭证 / 邀请 / 会话；
- 子表或引用表。

观察点：

- 列表页、详情页、编辑页、历史记录、跨页面入口是否还能正常呈现；
- 旧页面上继续操作时的提示与按钮恢复；
- 是否会误写、误删、串到其他记录；
- 是否泄露不属于当前用户的数据；
- 是否出现白屏、未捕获异常、裸露 SQL / 堆栈；
- 空态或“不存在”错误是否明确；
- 测试数据能否被清理脚本回收。

通用工具 `fixtures/delete_row.php` 可按表名与 ID 物理删除一条记录。项目如有子表或关联级联，应在项目自己的夹具中补充清理，或复制工具后扩展。破坏性用例必须使用专用测试数据，不能碰生产数据。

## 4. 输入数据格式与大小边界

对所有用户可填、接口可传、命令可带的数据，都要同时验证格式、长度和大小边界，不能只测合法值。

### 4.1 格式

- 数值：负数、0（不允许时）、超大值、小数 / 科学计数、数字字符串、空值、`null`、数组 / 对象。
- 标识：非法 ID、负数 ID、0、跨资源 ID、已删除资源 ID。
- 业务格式：版本号、日期、邮箱、URL、分支名、枚举、状态动作。
- 文本：纯空格、前后空格、纯符号、Unicode / 中文 / emoji、换行、HTML / 脚本 / SQL 特殊字符。
- 类型：字符串传数字、数字传字符串、布尔 / 数组 / 对象传标量；JSON 嵌套层级异常。
- 结构：必填缺失、重复字段、未知字段、空数组 / 空对象。

### 4.2 长度

- 空值、纯空格、最小长度、最大允许长度、最大长度 + 1。
- 按字符计数（`mb_strlen`）与按字节计数（数据库列长）分别考虑，中文 / emoji 容易暴露截断。
- 数据库列有长度上限时，超限必须是业务校验错误，不能把 SQL 截断 / `SQLSTATE[22001]` 直接暴露给用户，也不能静默截断后写入。
- 超长文本、超长名称、超长描述、超长 URL / 分支名分开覆盖。

### 4.3 大小与数量

- 请求体过大、单字段过大、列表一次提交过多项。
- 分页参数：负数、0、超大 limit、超大 start_id、翻页越界。
- 批量操作中的部分非法项：应整体拒绝并说明，或明确跳过，不能部分成功后无提示。
- 文件 / 附件：空文件、超大文件、错误 MIME、扩展名与实际内容不一致。

### 4.4 期望行为

- 非法输入应返回明确的业务校验错误，不能返回成功、静默修正、静默截断或原始数据库错误。
- 页面应显示可理解的提示，表单 / 按钮恢复，不能产生假成功或未捕获异常。
- 合法边界值（恰好等于最大长度等）应正常通过；非法值不应写入任何数据。
- 错误信息不应泄露 SQL、堆栈、内部表名等实现细节。
- 输入边界用例同样按边界清单设计，不以覆盖率作为锚点；写数据的成功路径和应被拒绝的路径都要做落库校验。

## 5. 可逆操作与回滚

需要覆盖的可逆/回滚角度：

- 数据库迁移的 `rollback`、批次回滚、重置；
- 批量导入 / 数据修复的回退；
- 版本回退、发布撤销、软删除恢复；
- 队列任务的暂停、恢复、重放；
- 配置变更的撤销。

验证点：

- 正向操作产生的结构 / 数据确实被撤销；
- 追踪记录（批次、版本号、审计日志）同步清理或标记；
- 依赖对象一起恢复，不留下半完成状态；
- 连续执行两次是安全的空操作，或给出明确错误；
- 回滚中途失败时保留诊断信息、退出码非 0、不静默成功；
- 不触碰主数据；使用隔离项目副本 + 临时数据库 / 命名空间。

通用工具 `fixtures/rollback_probe.sh` 展示了隔离回滚验证：复制项目、创建临时数据库、执行真实 `migrate:rollback`、检查 down SQL 与批次记录，并再次回滚验证幂等。其他可逆命令可参考同样的隔离思路。

## 6. 组合场景

单一失败往往不够，应按状态组合扩展：

- 接口失败 + 数据已被删除；
- 重试 + 数据状态已变化；
- 多用户 / 不同权限 + 资源被删除；
- 删除关联数据 + 旧页面继续操作；
- 慢响应 + 重复点击；
- 回滚 + 依赖服务不可用。

组合场景的目标是发现状态不一致、假成功、卡死和越权，而不是堆叠无关步骤。组合场景的每一步写操作都要在结束时核对数据库的最终状态。

## 7. 数据落库校验（写数据必查）

**凡对数据有操作的用例，页面 / 接口操作完成后都要到数据库确认数据是否正确落库。** 页面提示、toast、接口 200 都只代表请求成功，不代表数据正确。

适用对象：

- 新增、修改、删除、状态流转、审批、分配、发布、撤销等写操作；
- 被业务规则拒绝的写入（必须确认没有新增或改动）；
- 批量操作（确认条数、部分失败处理和幂等）；
- 软删除（确认 `delete_time` 有值、列表不再返回）；
- 写主记录同时写关联记录 / 日志 / 队列的操作（确认关联数据与状态）。

检查内容：

- 目标行是否存在、是否存在重复行；
- 关键字段值是否与页面 / 接口输入一致；
- 状态字段、版本号、更新时间和软删除标记是否正确；
- 关联表、历史表、队列任务等副作用是否符合预期；
- 操作失败时是否留下半条记录、错误状态或残留关联数据。

通用查询工具：

```bash
# 成功写入：确认 1 行且字段正确
HARNESS_COVERAGE=0 php /var/www/test_usecase/fixtures/db_check.php \
  --sql="select id,name,status,delete_time from project where id = 900001" \
  --expect-rows=1 \
  --expect-json='{"name":"测试项目","status":"1"}'

# 应被拒绝的写入：确认没有新增
HARNESS_COVERAGE=0 php /var/www/test_usecase/fixtures/db_check.php \
  --sql="select id from project where name = '   '" \
  --expect-rows=0
```

用例结果中记录：

```json
{
  "mutates_data": true,
  "db_verification": {
    "passed": true,
    "checks": [
      {"table": "project", "id": 900001, "expect": "name=测试项目, status=1", "actual": "name=测试项目, status=1"}
    ]
  }
}
```

- 校验在页面 / 接口操作之后、清理数据之前执行，和用例在同一个步骤内完成。
- 校验不通过时，即使用户看到的提示正常，也要把用例标为 `failed`，并在 `actual` 写明数据库实际值。
- 缺少 `db_verification` 的写数据用例会被报告标记为「落库未校验」；`run-all.sh` 默认严格审计（`DATA_CHECK_STRICT=1`）。
- 需要项目特有的字段 / 关联校验时，可以在项目夹具里封装查询，但结果仍写入 `db_verification`。

## 8. 轮次迭代与覆盖率补测

每一轮都是一次完整的「前端 + 接口 + CLI」执行，覆盖率按整轮统计：

- **PHP**：本轮页面、接口、CLI、队列执行过的代码；下一轮开始前 `coverage-reset`。
- **JS**：本轮全部 Playwright 页面流程合并后的 V8 覆盖率；不是某一个页面、也不是某一次运行。

每轮结束后的动作：

1. 读本轮报告：通过率、失败清单、页面穿透审计、落库校验、PHP / JS 覆盖率。
2. 看未覆盖行：优先找**能通过页面触达**的未覆盖代码，补页面流程；页面确实不可达的，才补接口 / CLI，并写 `unreachable_reason`。
3. 执行 `coverage-trend` 对比上一轮：PHP 业务口径与 JS 覆盖率是否还在增长。
4. 用 `coverage-trend --plan` 生成下一轮计划，按未覆盖行和审计缺口写新用例；不要重复已经通过的同类用例。
5. 新开一轮（`round-status start` 或在上一轮结束后运行 `run-all.sh`），重复执行。

停止条件：

- 连续 **2 轮**（可配置）的 PHP 业务口径与 JS 覆盖率增量都小于 **0.5 个百分点**（可配置），且未覆盖行中没有可通过现有入口触达的代码；或
- 剩余未覆盖行都属于不可达 / 第三方 / 框架 / 环境代码，并已在报告中说明原因。

覆盖率是补测的导航，不是唯一目标：破坏性边界、接口不可用、数据丢失、写数据落库等行为用例即使不增加覆盖率，也必须保留并通过。

## 9. 用例记录与统计

- 一个可观察行为对应一条用例；名称写清业务动作和边界，例如“删除后再次提交”“接口失败后可重试”“创建后落库字段正确”。
- 失败 / 未执行用例必须记录 `expected` 与 `actual`；未执行也计入通过率分母。
- 不在报告里另设“已知问题”区；问题就是失败用例。
- 接口 / CLI 用例写 `via_page` 或 `unreachable_reason`，通过页面穿透审计。
- 写数据用例写 `mutates_data` 与 `db_verification`，通过落库审计。
- 破坏性用例通常无法用代码覆盖率锚定，应以边界清单驱动设计；但仍纳入全量通过率。
- 每个用例清理自己造出的数据；无法清理时要在报告中明确。

## 10. 安全与隔离

- 只在测试环境执行，使用专用测试账号与专用测试项目。
- 不修改生产数据，不执行无法恢复的破坏性命令。
- 回滚、迁移、批处理优先在隔离副本 / 临时数据库执行。
- 删除工具、回滚探针、数据库查询工具的参数与目标必须显式，禁止默认指向主数据库。
- 测试结束执行清理，避免残留影响下一轮。

## 11. 设计检查清单

- [ ] 正常路径有一条页面穿透用例？
- [ ] 页面不可达的参数 / 权限 / 状态分支有接口或 CLI 用例，并写了 `unreachable_reason`？
- [ ] 能从页面触发的接口 / CLI 用例写了 `via_page`，能对应到本轮页面用例？
- [ ] 接口失败、超时、非 JSON、鉴权失败各覆盖到没有？
- [ ] 负数 / 0 / 超大数字 / 非法 ID 是否验证？
- [ ] 空值、纯空格、最大长度、最大长度 + 1、中文 / emoji 长度是否验证？
- [ ] 非法格式（版本号 / 日期 / 邮箱 / URL / 分支名 / 枚举）是否拒绝？
- [ ] 超长字段是否返回业务错误而不是数据库原始错误或静默截断？
- [ ] 操作失败后按钮、表单、弹窗、loading 是否恢复？
- [ ] 页面打开前 / 后删除底层数据的行为是否验证？
- [ ] 关联数据删除、跨项目 / 跨用户数据隔离是否验证？
- [ ] 所有写数据用例是否在操作后查询数据库，确认字段、行数、状态、软删除标记正确？
- [ ] 被拒绝的写入是否确认数据库没有新增或改动？
- [ ] 写数据用例是否写了 `mutates_data` 与非空 `db_verification`？
- [ ] 可逆命令是否验证撤销结果、追踪记录和二次执行？
- [ ] 删除 / 回滚 / 查询是否在隔离环境，是否有清理？
- [ ] 失败用例是否记录期望与实际，是否计入通过率？
- [ ] 是否根据上一轮未覆盖行和 `coverage-trend` 生成并执行了下一轮补测？
